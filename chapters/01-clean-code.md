# 1. Clean Code

- Bad code slows teams toward zero productivity; messes compound until unmanageable. LeBlanc's law: later equals never.
- The grand rewrite fails: the tiger team races the old system for years and produces a new mess.
- Defending code quality is the programmer's job, like a doctor refusing to skip hand-washing. Schedule pressure is no excuse - the only way to go fast is to keep code clean at all times.
- Clean code (per the masters quoted): elegant and efficient, straightforward logic, minimal dependencies, complete error handling, does one thing well (Stroustrup); reads like well-written prose (Booch); readable and enhanceable by others, has tests, minimal API (Dave Thomas); looks like the author cared (Feathers); no duplication, expresses intent, minimal entities (Beck/Jeffries); "pretty much what you expected" (Cunningham).
- Code is read ~10x more than written. Making code easy to read makes it easier to write.
- Boy Scout Rule: check code in a little cleaner than you checked it out.
